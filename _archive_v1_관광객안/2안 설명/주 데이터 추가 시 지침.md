## 2. Phase 계획 — 어떤 순서로 붙이는가

### Phase 0 — 검증 3건 (계산 시작 전)

`2안 근거.md` §4 의 SQL 3개를 먼저 돌립니다.

```
① 국적 집중도       ← 실패하면 국적 축을 권역군으로 묶거나 폐기
② DS-056 희소성     ← 실패하면 업종 → 시간 → 국적 순으로 완화
③ 장기/단기 비율    ← 단기 비중 낮으면 관광 탭 미개설
```

**세 결과를 먼저 문서에 기록한 뒤** 화면 작업에 들어갑니다.
2안은 전제가 가설이므로, 가설 검증 전에 만든 화면은 폐기될 수 있습니다.

### Phase 1 — 최소 구성 (승인 1건, 0.4GB)

```
DS-056  국적 × 업종 × 동 소비   [승인 필요]   0.324GB
DS-026  국적 × 동 방문인구       [개방]        0.005GB
DS-048  블록 × 업종 가맹점 실재  [개방]        0.067GB
```

이 3종으로 **탭 1(국적별 소비 지도)과 탭 2(내·외지인 구조)가 완성**됩니다.
시간대 기능만 비활성입니다.

→ 친화도 = `min(분위 DS-026 방문집중도, 분위 DS-056 LQ, 분위 DS-048 점포실재)`

### Phase 2 — 시간축·정주성 (승인 0건, +1.7GB)

```
DS-017  국적 × 동 × 시간대(0~23)  [개방]  0.108GB  → 적정 시간대
DS-028  국적 × 동 × 숙박일수      [개방]  0.001GB  → 장기/단기 정밀화
DS-047  동 × 업종 × 시간대        [개방]  1.563GB  → 업종 영업 시간대
DS-076  동 × 전입 외국인수        [개방]  0.013GB  → 타겟 규모·온보딩
DS-022  시군구 × 국적 × 시간대    [개방]  0.033GB  → 경기 31개 시군 비교
DS-027  시군구 × 국적             [개방]  0.001GB  → 동일
```

→ 이 시점에 **탭 3(동선)의 시간 배치와 탭 4(안산 특수성)가 켜집니다.**
전부 대민개방이라 승인이 필요 없습니다.

### Phase 3 — 동선·유입 (승인 2건, +17GB)

```
DS-004  행정동간 OD × 이동목적  [개방]     9.020GB  → 동→동 전이 (동선 연결)
DS-005  행정동간 OD × 이동수단  [개방]     8.114GB  → 구간별 이동수단
DS-050  블록 × 유입지 × 업종    [승인]     8.342GB  → 서울 어디서 오나
DS-054  블록 × 1시간 매출       [승인]     3.129GB  → 블록 해상도 시간대
```

DS-004·005는 개방이지만 각 8~9GB라 chunk 또는 DuckDB가 필요합니다.
**안산 관련 행(O 또는 D가 4127*)만 먼저 필터링**하십시오.

### Phase 4 — 관광 축 (조건부)

Phase 0 ③에서 단기 비중이 임계 이상일 때만.

```
DS-001  시군구 OD × 목적 × 수단 × 시간대  [개방]  98.255GB  ← 목적=4(관광)만 추출
DS-006  시군구 OD 월별 (202301~202604)   [개방]   6.198GB  ← 40개월, 시계열 최장
DS-011  동 × 체류시간 × 목적             [개방]   0.939GB  ← 통과 vs 체류
```

DS-001은 98GB이므로 **목적=4 + 도착지 4127* 로 먼저 자른 뒤** 사용합니다.
관광 축을 채택하지 않으면 Phase 4 전체를 받지 않아도 됩니다.

## 3. 쿼리 원형

### ① LQ (입지계수) — 2안의 핵심 계산

```sql
WITH base AS (
  SELECT admi_cty_no AS adm, card_tpbuz_nm_3 AS biz, nt,
         SUM(amt) AS amt, SUM(cnt) AS cnt
  FROM ds056
  WHERE cty_rgn_no LIKE '4127%'
    AND ta_ymd BETWEEN '20260101' AND '20260630'
  GROUP BY 1,2,3
),
dong_nat AS (SELECT adm, nt, SUM(amt) AS amt FROM base GROUP BY 1,2),
city_biz  AS (SELECT biz, SUM(amt) AS amt FROM base GROUP BY 1),
city_all  AS (SELECT SUM(amt) AS amt FROM base)
SELECT b.adm, b.biz, b.nt, b.cnt,
       (b.amt / dn.amt) / (cb.amt / ca.amt) AS lq
FROM base b
  JOIN dong_nat dn ON b.adm = dn.adm AND b.nt = dn.nt
  JOIN city_biz  cb ON b.biz = cb.biz
  CROSS JOIN city_all ca
WHERE b.cnt >= 5;            -- 마스킹
```

`lq > 1` = 그 국적이 그 동에서 유별나게 많이 쓰는 업종.

### ② 국적별 동 방문 집중도

```sql
SELECT ADM_CD, CNTRY_NM,
       SUM(POP) / SUM(SUM(POP)) OVER (PARTITION BY CNTRY_NM) AS visit_share
FROM ds026
WHERE SGG_CD LIKE '4127%' AND IN_FORN_DIV_NM = '1'   -- 장기
GROUP BY 1,2;
```

★ **분모는 반드시 DS-026(중복배제)** 입니다. DS-017은 시간대별 방문 기준이라
같은 사람이 여러 시간대에 중복 계수됩니다. 비율의 분모로 쓰면 과소평가됩니다.

### ③ 내·외지인 구조 (원안 2) — `nt` 한정이 핵심

```sql
SELECT admi_cty_no AS adm, card_tpbuz_nm_3 AS biz,
       SUM(CASE WHEN gb='01' THEN amt END) / SUM(amt) AS local_share,
       SUM(CASE WHEN gb='02' THEN amt END) / SUM(amt) AS near_share,
       SUM(CASE WHEN gb='03' THEN amt END) / SUM(amt) AS far_share,
       SUM(amt) / SUM(cnt)                            AS ticket   -- 순위만 사용
FROM ds056
WHERE cty_rgn_no LIKE '4127%'
  AND nt = :domestic_code        -- ★ 내국인 한정. 빼면 전부 오답
GROUP BY 1,2
HAVING SUM(cnt) >= 5;
```

`gb` 정의에 **"외국인의 경우 모두 외지인"** 이 명시돼 있습니다.
`nt` 한정을 빼면 원곡동 거주 외국인의 소비가 '외부 유입'으로 집계됩니다.

### ④ 적정 시간대 (두 곡선의 min)

```sql
-- DS-017: 국적 × 동 × 정시 0~23
WITH nat_h AS (
  SELECT ADM_CD, CNTRY_NM, CAST(TIMEZN_CD AS INT) AS h, SUM(POP) AS pop
  FROM ds017 WHERE SGG_CD LIKE '4127%' GROUP BY 1,2,3
),
-- DS-047: 동 × 업종 × 2시간 버킷. hour='01' 은 7시간이라 제외
biz_h AS (
  SELECT admi_cty_no AS adm, card_tpbuz_nm_2 AS biz, hour, SUM(cnt) AS cnt
  FROM ds047 WHERE admi_cty_no LIKE '4127%' AND hour <> '01'
  GROUP BY 1,2,3
)
-- nat_h 의 정시를 biz_h 의 버킷으로 내린 뒤 각각 분위화하고 min
SELECT ...;
```

**`hour='01'` 은 00:00~06:59 (7시간)** 입니다(07 코드값사전).
정시 절단이 안 되므로 계산에서 제외합니다. 3안과 동일한 대응입니다.

### ⑤ 동→동 전이 (동선 연결)

```sql
SELECT O_ADMI_CD, D_ADMI_CD, PURPOSE, SUM(CNT) AS n
```

## 5. 업종 그룹 정의 — 코드표가 오면 즉시 채울 표

카드 업종코드 전체 목록이 없어 **의도만 정의해 둡니다**(파라미터 #9, C등급).

| 목적군 | 데이터에서 찾을 것 | `card_tpbuz_nm_3` 매핑 |
|---|---|---|
| 장보기 | 식료품 소매 · 종합 소매 · 정육 · 수산 | (채울 것) |

| 미용 | 이용 · 미용 | (채울 것) |

## 6. 데이터가 들어오면 반드시 다시 확인할 것

1. **Phase 0 검증 3건의 결과를 문서에 먼저 기록.**
   국적 집중이 없거나 DS-056 셀이 너무 희소하면 **그것이 결론**입니다.
   설계를 바꾸거나, 2안을 6안·7안처럼 실행불가 사유서로 전환합니다.

2. **`nt` 값의 실제 분포.** `'000'` 이 내국인인지 확인하고, 관측되는 국적코드
   수를 셉니다. 21개국이라지만 안산에서 실제로 관측되는 것은 더 적을 수 있습니다.

2-1. **★ 국적 키 정합 — 이것을 못 맞추면 친화도 계산이 안 됩니다.**

```
통신 (DS-017 · 026 · 028) : CNTRY_NM = 한글 국적명 텍스트   실측 예시 '중국'
카드 (DS-056)             : nt       = 3자리 코드           실측 예시 '000'
```

   친화도 `min(vs, lq, alive)` 는 `vs`(DS-026)와 `lq`(DS-056)를 **같은 국적으로
   묶어야** 성립하는데 두 데이터의 키 체계가 다릅니다.

```python
# 도착 직후 반드시 확인할 것
set(ds026.CNTRY_NM.unique())   # 한글 국적명 몇 개가 실제로 관측되는가
set(ds056.nt.unique())         # 코드 몇 개가 실제로 관측되는가
# → 두 집합의 크기가 다르면 매핑에 결손이 생김. 어느 쪽이 더 세분화됐는지 먼저 판정
```

   **매핑표를 만든 뒤 반드시 남기십시오** (`data/processed/nat_code_map.csv`).
   양쪽 모두에서 관측되는 국적만 서비스 대상이 되고, 한쪽에만 있는 국적은
   화면에서 제외한 뒤 **제외 사실과 사유를 한계 탭에 적습니다.**
   인벤토리에는 21개국 목록 자체가 없으므로(문구만 "기타 포함 21개국"),
   이 매핑표는 **실제 파일에서 만들 수밖에 없습니다.**

3. **DS-026(통신 추정) vs 행안부 외국인주민 현황(행정 실측)의 동별 순위 상관.**
   상관이 낮으면 통신 추정치를 그대로 시민 화면에 쓰기 어렵습니다.
   순위 상관계수를 근거 문서에 기록하십시오.

4. **`gb` 3분할의 합이 1인지.** `01+02+03` 이 전체와 일치하지 않으면
   분류 불가 건이 있다는 뜻이고, 비중의 분모를 재정의해야 합니다.

5. **마스킹 후 남는 국적 수.** 화면 드롭다운에 3개 국적만 남으면
   "국적별 서비스"라고 부를 수 없습니다. 그 경우 권역군으로 전환합니다.

6. **DS-056 18개월 시계열의 계절성.** 국적 데이터는 6개월뿐이지만 소비는 18개월이라,
   `nt` 한정 없는 동·업종 소비의 계절 패턴은 확인할 수 있습니다.
   라마단·설·추석 등이 보이는지 확인하면 해석의 설득력이 올라갑니다.
